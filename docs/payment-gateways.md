# Admin-managed payment gateways

> Historical repair checkpoint from the correction repository. See [repository-transfer.md](repository-transfer.md) for validation and blockers in SmartBridge-FET.


SmartBridge now has **Admin Dashboard → Payment Gateways** on the repair branch. The administrator can enable/disable Yoco and Paystack, choose test/live mode and set display order. Checkout loads enabled gateways with configured credentials and lets the customer choose. Both start disabled, so a Paystack account is not needed now.

Gateway settings contain no keys. Credentials remain server-side, separated by provider and test/live mode. The panel reports whether credentials are configured, shows the callback address and blocks enabling an unconfigured mode. This checks configuration presence/format, not merchant approval or successful payment processing. Credentials are provisioned in the hosting project's secret settings; this panel does not accept or display private keys. An app-wide pause message explains when checkout deployment flags remain off.

## Account setup later

1. Create your Yoco or Paystack merchant account and confirm that it supports the intended ZAR payments.
2. Configure its test credentials securely. Use `YOCO_TEST_SECRET_KEY` and `YOCO_TEST_WEBHOOK_SECRET`, or `PAYSTACK_TEST_SECRET_KEY`. Existing Yoco settings remain compatible with the configured `YOCO_MODE`.
3. Register the displayed provider callback address and verify test checkout/callback journeys in staging. Paystack signs callbacks using its secret key; Yoco supplies a separate signing secret.
4. In Payment Gateways, select test mode, enable the provider and save. Customers see it only when checkout is also activated for the app.
5. Configure and verify live credentials separately before switching to live mode. Mode changes turn the UI toggle off until explicitly enabled and saved.

The fifth migration stores gateway preferences, records administrator changes in a private audit table and binds each payment order/receipt to its provider. Only database-authorized administrators can change preferences. Ordinary users cannot change gateway settings or use another provider's callback to fulfill an order. Disabling a gateway stops new checkout sessions; valid outstanding payments can still settle with their original mode credentials. Keep old-mode secrets until outstanding payments and provider retries are reconciled.

Yoco uses its existing signed checkout callbacks. Paystack initializes transactions on the server with authenticated email, server price, fixed callback and a stable reference. Its raw-body HMAC SHA-512 signature is verified, then the transaction is checked directly with Paystack before atomic fulfillment. Test payments do not grant premium. The ledger deduplicates callbacks and preserves the paying account's ownership. Unexpected large numeric Paystack IDs fail closed for manual reconciliation rather than losing precision.

## Adding another provider

The provider catalog and adapters are separate from checkout UI and subscription fulfillment. A new gateway needs a reviewed server connector, credential configuration, signature/payment verification, allowed redirect hosts and registry/schema migration. Once supported, it can be managed through the same admin panel; the main checkout and subscription pages need no provider-specific rewrite. An arbitrary gateway name or API URL cannot be enabled without a connector. No additional merchant accounts or paid services were created.

One-off premium purchases are supported. Recurring billing, refunds/chargebacks, booking payment collection, tutor payouts and ambiguous/expired checkout recovery remain separate work. Paystack's stable reference prevents blindly creating a new payment intent after an uncertain initialization, but duplicate initialization errors require reconciliation; no undocumented provider idempotency behavior is assumed.
